# Astronauts 引擎脚本格式逆向分析

样本：`憑夜ノ村`（Astronauts, 2014）`bincode.gxp` → `bincode/moacode.mwb`

| | |
|---|---|
| `bincode.gxp` | 692,523 字节 · sha256 `d09a412f469388c39c9fb4eb310399fead26533385580e11b8b5c00ef9eb0ba5` |
| `moacode.mwb` | 683,189 字节 · sha256 `1975e644cd08939e40fa9927269efe8484edf4abb2c29eaf128abd45f40e4a10` |
| 解压载荷 | 5,237,260 字节 · sha256 `73d6ba82c6480167925681a6c26b4eccae20d0f9edd70ddfb9915e49a4205858` |
| 申报深度 | **T2 anchor-resolved**（token 流完全切分 + 语句/参数锚点已解析） |
| 字节覆盖 | **1.0**（5,237,260 / 5,237,260，0 未知字节） |
| 零编辑往返 | **逐字节一致**（`.mwb` 与 `.gxp` 整文件哈希相同） |

宿主 `憑夜ノ村.exe` 未加壳，字符串区含 `BMOA` / `TMOA` / `ZMOA` 三个容器签名与
`moacgui.exe`、`scripts`、`bincode`、`-a`、`-mc` 等编译器调用痕迹——说明 `.mwb` 由
外部编译器 `moacgui.exe` 从 `scripts/*.txt` 生成。`bincode/modlist.dat`（UTF-16LE
纯文本）保留了编译时的源清单：71 个脚本文件加时间戳，路径为
`C:/Users/kusu/Desktop/マスター/scripts/…`。

---

## 1. 层次结构

```text
bincode.gxp                       GXP 归档（小端）
  └ bincode/moacode.mwb           条目 0，XOR 加密
      └ ZMOA 头 0x1C 字节（小端）
          └ zlib 流
              └ token 流（大端）        ← 5,237,260 字节，本文分析对象
                  ├ R_HEADER  [0, 10219)         标签表 + 内建函数表
                  └ R_CODE    [10219, 5237260)   语句流，47,251 条语句
```

**字节序是混合的**，这是最初的主要误判来源：GXP 外壳与 ZMOA 头为小端，
zlib 载荷内的全部 token 参数为大端。判据（`EV_ENDIAN`）：

- `ZMOA` 头 `0x14` 处字节 `0c ea 4f 00` 小端读作 5,237,260 = 实际解压长度；
  大端读作 216,682,240，与文件不符。
- 字符串 token `1a 00 00 00 09 6d 61 63 72 6f 2e 74 78 74 00` 中长度字段
  `00 00 00 09` 大端读作 9 = `macro.txt` 的字节数；小端读作 0x09000000。

## 2. GXP 归档

```text
0x00  'GXP\0'
0x04  u32  version        100
0x08  u32  magic2         0x10203040
0x0C  u32  flag0          1
0x10  u32  flag1          0
0x14  u32  flag2          1
0x18  i32  entry_count    2
0x1C  u32  index_size     144
0x20  u32  data_size      692331
0x24  u32  reserved       0
0x28  i64  base_offset    192  (= 0x30 + index_size)
0x30  索引区（每条 entry_size 字节，加密）
base  数据区（每条独立加密）
```

索引条目（解密后，小端）：

| 偏移 | 宽度 | 含义 |
|---|---|---|
| 0x00 | u32 | `entry_size`，本条索引长度（自校验字段） |
| 0x04 | u32 | 文件长度低 32 位 |
| 0x08 | u32 | 文件长度高 32 位 |
| 0x0C | u32 | 名字的 UTF-16 字符数 |
| 0x10 | u64 | 时间戳类字段，原样保留（本作两条为 `0x1cfffca_dd2092a2` / `…dd2155f3`） |
| 0x18 | i64 | 相对 `base_offset` 的数据偏移 |
| 0x20 | — | 名字（UTF-16LE），其后填充至 `entry_size`（本作各条尾部 2 字节） |

加密为逐字节 XOR：`b ^= (i & 0xFF) ^ KNOWN_KEY[i % 23]`。

**关键细节：`i` 从每个缓冲区自身起始计数，而非全归档连续计数。** 每条索引条目
与每条数据条目各自从 0 重新开始。首次实现按连续计数，结果第一条正确、第二条起
全错（9,117 字节不符）——这类错误不会被条目 0 的校验发现，只有整归档逐字节
往返才能暴露。

条目长度密钥 `entry_key = K[0] | (1^K[1])<<8 | (2^K[2])<<16 | (3^K[3])<<24`
= `0x3b2a2040`。本作固定密钥即可解开；实现保留了归档名兜底密钥路径
（`arcname[i % len]` 再 XOR 一次），仅在固定密钥解析失败时尝试。

## 3. ZMOA 容器

```text
0x00  'ZMOA'
0x04  u32  0
0x08  u32  0
0x0C  u32  0
0x10  u32  version        100
0x14  u32  uncomp_size    5237260
0x18  u32  comp_size      683161   (= 文件长度 - 0x1C)
0x1C  zlib 流（78 9c …）
```

**零编辑逐字节往返要求复用原始压缩参数。** 穷举 level 0–9 × 5 种 strategy ×
memLevel 8/9 后确定：`level=6 / Z_DEFAULT_STRATEGY / memLevel=8 / wbits=15`
（即 zlib 默认）复现原始 683,161 字节流，逐字节一致（`EV_ZLIB_PARAMS`）。
用 `level=9` 会得到 668,703 字节的不同流——内容等价，但整文件哈希不同，
于是"零编辑重建"退化为只能验证载荷相同，而无法验证整文件相同。

头部 `0x20` 起曾被误判为 28 字节哈希字段，实为 zlib 数据的一部分：
`comp_size` 与 `len(file) - 0x1C` 相等即证明压缩流从 `0x1C` 起始，中间没有
额外字段。该文件不含校验和。

## 4. Token 语法

体系结构：**无栈无寄存器的标记流**。不是传统 VM 字节码，而是编译器输出的
参数化命令序列——每条语句由命令 id、参数标记对与字符串值组成，解释器顺序读取。
因此不存在跳转偏移、基本块或指令边界歧义，这也是能达到 100% 字节覆盖的原因。

九种 token，`tag` 为首字节，参数为大端：

| 名称 | tag | 布局 | 长度 | 实测数量 |
|---|---|---|---|---|
| `STR` | `0x1A` | `tag + u32 len + len 字节 + 0x00` | 变长 | 92,652 |
| `REF` | `0x00` | `tag + u24` | 4 | 47,251 |
| `REFE` | `0xFF` | `tag + u24`（值恒 `0xFFFFFF`） | 4 | 252 |
| `INT` | `0x05` | `tag + i32` | 5 | 870 |
| `P15` | `0x15` | `tag + i32` | 5 | 191,371 |
| `P06` | `0x06` | `tag + i32` | 5 | 191,375 |
| `END` | `0x07` | `tag + i32` | 5 | 47,503 |
| `MARK` | `0x21` | `tag` | 1 | 94,918 |
| `BLK` | `0x20` | `tag + i32` | 5 | 94,918 |

合计 761,110 个 token，覆盖 5,237,260 字节，**零未知字节**（`EV_TOKEN_COVERAGE`）。

### 4.1 两个易错的长度判定

`REF`/`REFE` 的参数是 **u24（3 字节）而非 u32**。按 u32 解析会吞掉下一个 token
的 tag 字节：`00 00 03 8a | 1a 00 00 00 08 msg.hide` 中，若 `REF` 取 4 字节参数
就会消费掉 `0x1a`，导致后续字符串全部错位。判据是 u24 解析后 `STR` 的终止符
恒好落在 `len` 之后（92,652 次全部成立）。

`MARK`（`0x21`）**无参数**。它总是紧跟 `BLK`（94,777 次），因此看起来像
5 字节的 `21 20 xx xx xx xx`，但另有 141 处 `21 21` 与 `21 20 …` 独立出现，
证明二者是独立 token。

### 4.2 语句模型

```text
语句 := REF(id) [STR(name)]
        ( P15(a) P06(k) [STR(v)] | MARK BLK(x) )*
        END(0)
```

- `END(0)` 是唯一终止符，共 47,251 个，与 `REF` 语句头数量**恰好相等**。
- `END(-1)` **不是**终止符：它引导 `REFE(0xFFFFFF) STR(label)`（标签引用），
  语句在其后继续。252 处 `END(-1)` 全部紧跟 `REFE + STR`。
  最初把 `END(-1)` 当终止符，导致 `go`/`gosub` 类语句被截断在标签之前。
- 40,595 条语句带内联函数名（`REF` 后紧跟 `STR`），6,656 条只有 id
  （前一个 token 恒为 `END`，即均为合法语句头）。
- token 0–1190 属 R_HEADER，不归任何语句；1191 起每个 token 恰属一条语句，
  无重叠、无遗漏。

### 4.3 R_HEADER 两张表

```text
标签表项：STR(label) INT(line) INT(0) STR(file) INT(kind)
函数表项：STR(name)  INT(id)   INT(-1) INT(1)
```

**函数表的名字在 id 之前**，不是之后。按 `INT(id) INT(-1) INT(1) STR(name)`
读取会得到整体错位一项的映射表（`910 → sel.go` 而非 `text`），进而使全部语句的
函数名标注偏移一格。修正后 154 个 id → 名字绑定与代码区 40,595 条内联名字**完全一致**，
这个一致性本身就是该表布局的证明（`EV_FN_TABLE`）。

标签表把标签映射到 `(源文件, 行号)`，而非字节偏移——因此 `INT` 参数最大值仅
40,013（源码行号量级），远小于载荷长度 5,237,260。这一点对回封至关重要（见 §6）。

已识别的命令 id（节选）：

| id | 名称 | id | 名称 | id | 名称 |
|---|---|---|---|---|---|
| 64 | `go` | 910 | `text` | 1500 | `bgm` |
| 65 | `goif` | 911 | `endtext` | 1520–1524 | `se`…`se_3` |
| 66 | `gosub` | 1016 | `sp.clearall` | 1530 | `vo` |
| 68 | `return` | 1020 | `stand` | 2000 | `sel` |
| 200 | `rand` | 1021 | `endstand` | 2001 | `sel.go` |
| 830 | `setgamedatatitle` | 1100 | `bg` | 2101 | `wa.time` |
| 840 | `getreplaymode` | 1200 | `ev` | 2200/2204 | `rp.set`/`rp.end` |
| 906 | `msg.hide` | 1310/1311 | `flash`/`flash.wa` | 11000 | `jumptotitle` |

另有 5,540 条语句的 id 不在函数表中（600、1000、250、50、400…），按
`cmd_<id>` 呈现。它们的参数形态与同类具名语句一致（多为舞台效果），
语义未确认，如实标为未解析而非猜测。

## 5. 参数是位置式，不是语义式

这是本次分析中**最容易误判、且误判不会被任何字节门禁发现**的一点。

`P15(a) P06(k)` 成对出现（191,371 对，仅 4 处落单）。最初的读法是
"`P06` 的编号 = 参数语义"，于是把 `40` 读作"人名"、`35` 读作"voice"。
该读法在 `text` 语句上恰好成立，因此看起来正确——直到统计其他函数：

```text
attr 40 的取值：栞/智樹/萌香（人名）  但也有 Ｈ（射精音…）、民家部屋_夜消灯、ドア（ふすま）
attr 35 的取值：sio0001（voice）      但也有 T、左から右へ、円形（中から外へ）
```

对 14,211 条带串参语句做位置统计后得到正确模型（`EV_POSITIONAL_ARGS`）：

| | |
|---|---|
| 首参 `attr=40` | 12,986 条 |
| 首参 `attr=35` | 1,031 条 |
| 首参 `attr=14` | 192 条（对象引用槽，非位置参数） |
| `attr=40` 出现在非首位 | 13 条，且全部是 `attr14/p2` 对象引用先出现的情形 |

即 **`attr40` = 第 0 个位置参数，`attr35` = 后续位置参数**，编号本身不含语义。
文本角色由 `(函数, 位置序号)` 共同决定：

```python
ARG_TAGS = {
    "text":             ("name", "voice"),     # arg0 = 说话人, arg1 = voice id
    "setgamedatatitle": ("ui",),               # arg0 = 存档章节标题
    "stand"/"bg"/"ev"/"bgm"/"se*"/"vo": ("res", "effect"),
    "go"/"goif"/"gosub"/"rp.*":         ("label",),
}
```

`P06` 的另一类取值是**值类别**（出现在 `P15(4)` 之后）：`8` = 正文、
`5` = 位置参数串值、`2` = 对象名、`65543` = 选项跳转目标、`65545` = 条件跳转目标、
`327687` = 宏名、`393225` = 变量名。

### 5.1 sel 的两个形态

`sel`(2000) 共 336 条，同一槽位承载两种完全不同的内容。按取值外观区分
（"像句子的是选项"）是不可靠的启发式；正确判据是结构性的
（`EV_SEL_SHAPES`，§7.1.3 形态派发）：

| 形态 | 判定条件（纯谓词） | 数量 | 位置参数语义 |
|---|---|---|---|
| `sel.menu` | 语句内存在 `P06(65543)` 跳转目标 | 2 | 选项文本 |
| `sel.stage` | 无跳转目标 | 334 | 资源名 / 转场效果名 |

两形态均显式声明，无命中即抛错。这条判据把 `choice` 从 13 条误报收窄到
3 条真实选项（`今は決められない` / `契りを交わす` / `何も答えずに黙っている`，
分别跳向 `@YES_KUR` / `@NO_KUR`）。

### 5.2 含日文却必须 frozen 的字符串

对 131 个字符串槽位类做全量清点后，仍有 4,815 条 `frozen` 字符串含日文假名。
逐类核对确认全部是**资源查找键**（`EV_ASSET_KEYS`）：

| 例 | 槽位 | 性质 |
|---|---|---|
| `布ずれ（シュ）` `足音（草むら歩く＿複数）` | `se`/`se_0`/`se_1` arg0 | SE 名 |
| `村長の屋敷部屋_昼` `集落を通る道_夜` | `bg` arg0 | 背景名 |
| `左から右へ` `円形（中から外へ）` `T` | arg1 | 转场效果名 |
| `栞.COLOR` `萌香.SHAKE` | `attr14/p2` | 对象属性引用 |
| `VAR_02_あおゑエッチ既読` | `p393225` | 变量名 |

翻译这些会导致素材加载失败。判定依据是函数与参数位置，不是取值外观。

### 5.3 文本分类结果

| tag | 条数 | 策略 | 说明 |
|---|---|---|---|
| `msg` | 15,568 | translatable | 正文（合并后；原 26,160 页） |
| `name` | 8,381 | translatable | 说话人名 |

| `choice` | 3 | translatable | 选项文本 |
| `label` | 389 | frozen | 跳转目标 |
| `misc` | 57,656 | frozen | 函数名、表项名、资源键 |

`tag_source` 全部为 `structural`，`heuristic` 与 `unresolved` 均为 **0**——
没有任何条目依赖外观推断。

### 5.4 多页正文按语句合并

`text` 语句内的正文被消息窗按行拆成多个"页块"，但**本质是一句话**：

```text
「先輩が村長と話があるって……それから、屋敷に      ← 页 1
   行って……それで、先輩が……村に……」            ← 页 2
```

页块布局（15,568 条语句**全部符合，零例外**，`EV_PAGE_BLOCK`）：

```text
MARK BLK(1) P15(4) P06(8) STR      相邻页 STR 下标间距恒为 5，框架 22 字节
```

因此按语句聚合导出为一条，页边界写作字面 `\n`（反斜杠 + n 两个字符——
双行文本是逐行格式，真换行会破坏行结构）：

| 每条页数 | 语句数 |
|---|---|
| 1 | 6,308 |
| 2 | 7,928 |
| 3 | 1,332 |

合并后 26,160 页 → 15,568 条完整句子，与 `text` 语句数一一对应
（这也是 `sanity.msg_matches_statements` 门禁的判据）。译者面对完整句子，
不必猜测断行处如何衔接；回封时按 `\n` 重新分页，**页数可增可减**。

为使往返无歧义，该模式下原文中的字面反斜杠会转义为 `\\`。实测本样本
92,652 条字符串含反斜杠者为 0，该转义仅为防御性保证。

### 5.5 剧情分段

代码流以 `go <章节名>` 作为剧情跳转分界。判据（`EV_CHAPTER_BOUNDARY`）：
跳转目标出现在头部标签表中、映射到 `.txt` 源文件、且不以 `@` 开头
（`@` 前缀是文件内的局部标签，如 `@SKIP2`、`@YES_KUR`）。

实测 67 个边界，性质完备：

```text
语句序号严格递增          （可直接用于二分归属）
区间连续无缝              （末段止于 47251 = 语句总数）
24,015 条可翻译条目全部归属，零遗漏
每段映射到唯一源脚本      （共通＿01 → 共通＿01.txt，与 modlist.dat 一致）
```

与 `modlist.dat` 的 71 个编译源相比少 4 个，差额是未被 `go` 引用的
`macro.txt` / `vars.txt` / `sys/builtin.txt` / `sys/define.txt` 等非剧情脚本——
它们的字符串归入 `_00_prologue.txt`，不丢弃。

`スタッフロール` 被 `go` 引用 3 次（三个结局各一次），文件名追加序号避免互相覆盖。

因此默认按段导出 64 个文件（`01_共通＿01.txt`…），与原始脚本结构对应；
`--single-file` 可退回单文件模式。分章导出与整份导出的条目总数相等，
这是 `chapters.split_equals_whole` 门禁的判据。

## 6. 回封：为什么变长是安全的

申报 T2，允许 `identity` / `in_place` / `pointer-rewrite`，**不允许**
`full-layout`（那需要 T3 指令级理解）。

变长安全的根据是**流内不存在字节偏移引用**：

- `INT` 参数范围 `[-1, 40013]`，全部是源码行号，远小于载荷长度 5,237,260。
- `BLK` 参数范围 `[0, 3708]`，为子操作码与行号。
- 遍历全部 `INT`/`BLK`/`REF`/`P06`/`P15` 参数，值恰好等于某 token 偏移
  且 > 0x1000 的仅 10 处，逐一核对均为巧合（行号/参数编号），非引用。

字符串长度字段内联于 `STR` token 自身，因此：

| 改动 | 影响范围 | 是否需要重定位 |
|---|---|---|
| 单页文本变长/变短 | 该 `STR` token 内部 | 否 |
| 多页正文改变页数 | 该页块序列整体重写 | 否（无外部引用指向页块） |

页数变化会改变 token 总数，验证时按 `页数变化 × 5` 精确核算——这是"长度差
必须可解释"在本格式的具体形式。

### 6.1 回封后的验证项

```text
□ 输出可被自身完整重新解析
□ 重解析后字节覆盖仍为 1.0
□ 语句数与每条的 (id, 函数名) 绑定完全不变
□ token 数变化 == 页数变化 × 5
□ 字符串序列与预期逐条相同（同时覆盖"编辑生效"与"未编辑不变"）
□ 长度差 == Σ(新页块字节 - 旧页块字节)
□ 有编辑时哈希必须改变；零编辑时必须逐字节相同
```

倒数第二条与最后一条判定方向相反，互为对照——缺任一条都无法发现方向写反。

## 7. 验证结果

## 8. 未决问题

如实申报，不做猜测：

1. **5,540 条语句的命令 id 不在内建函数表中**（600、1000、250、50、400、
   3000、4000、5000、130、220、350、1050…）。参数形态与具名舞台语句一致，
   推测为效果类命令，但宿主内未找到对应名字表，故按 `cmd_<id>` 呈现。
2. **57 条语句的 id 高位置位**（u24 读作 0x800000 以上，如 `0xffe8cc`、
   `16771276`）。语法上是合法语句头（后随 `P15`），但 id 空间含义未确认。
   按 u24 原值保留，回封时逐字节不变。
3. **`BLK` 子操作码语义未全部确认**。已知 `0` = 闭合、`1` = 开、`2` = 续，
   其余（4/5/7/9/12/13/14）为子操作，具体行为未逆向。不影响文本提取与回封，
   因为它们原样保留。
4. **`P15` 的取值含义**（0/1/4/5）只确认了 `0` = 位置标记前缀、`4` = 后随串值；
   `1` 与 `5` 出现在无值参数处，语义未确认。
5. **未做跨样本验证**。同引擎其他作品（Astronauts 的 `BMOA`/`TMOA` 容器）
   未获取样本，形态签名分布无法对比。这是已知风险：若换作品后
   `shapes` 门禁报出未声明形态，说明需要新增形态声明而非修改结构逻辑。
6. **`modlist.dat` 未纳入回封流程**。它是编译期源清单（路径+时间戳），
   不影响运行；解包会导出，封包时原样保留。
