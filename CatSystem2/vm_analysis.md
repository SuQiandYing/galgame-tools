# CatScene (.cst) 格式逆向分析与证据台账

引擎标识 `CATSCENE_CS2`，方言 schema `1.0.0`，工具 `cst-tool/1.0.0`。

本文件是 `opcodelist.py` / `disassembler.py` / `assembler.py` / `run_gui.py` 共同的
唯一真值源。每个方言数值在此登记来源，`§1.2` 要求的两条独立证据也在这里。

## 1. 体系结构结论

CatScene **不是字节码 VM**。载荷里没有操作码流，只有一张 **偏移表 + 变长文本记录流**：
每条记录是 `01 <type> <payload…> 00`，`type` 只有四个取值，`payload` 是**明文命令行或对白**。
命令由引擎在运行时按空格切词解释（`cg 0 blend 0`、`if (#(1060+0)==0) …`），
不预编译成数值。

因此：

- 不存在指令边界问题，`instruction_coverage` 恒为 `not_applicable`。
- 申报 **T2**（锚点已识别定位）而非 T3：记录边界已完整解析、每字节唯一归属，
  但命令**参数的语义**未逐条逆向（`attr_def 401 402 403 404 405` 五个数各指什么未确认）。
  按 §1.3，T2 已足以支持 `roundtrip` / `in_place` / `pointer-rewrite`，正是本工具申报的能力。
- 记录区间在证书里标 `T3`（边界与类型完整无缝无重叠），但层的 `min_tier` 取全局最低值 T2。

## 2. 层栈

```text
L000 容器   [0,16) 头 + [16,16+comSize) zlib 流
L001 载荷   zlib 解压结果：载荷头 + 块表 + 偏移表 + 记录流
```

### EV_MAGIC — 魔数 `CatScene`
- 证据等级：`observed`
- 来源：全部 980 个样本的前 8 字节均为 ASCII `CatScene`；宿主 `InnocentGirl.exe`
  偏移 `0x269E10` 与 `0x269E1C` 各有一份该字符串常量。
- 交叉验证：同目录 `InnocentGirl.exe` `0x25D9C8` 处有 `cst`、`0x25D9D4` 处有 `.cst`，
  与 `scenelist.csv`、`scene` 相邻，构成「场景脚本扩展名」这一组常量。
- 反例检查：目录内非 `.cst` 文件（`.int`、`.hg3`）不以该魔数开头。

### EV_HEADER16 — 16 字节容器头
- 证据等级：`derived`
- 来源：`[8,12)` = 压缩长度，`[12,16)` = 解压长度，小端 u32。
- 交叉验证一：980/980 个文件满足 `16 + comSize == filesize`（尾部零字节未归属）。
- 交叉验证二：980/980 个文件满足 `len(zlib.decompress(stream)) == uncSize`。
- 反例检查：把 `uncSize` 改成任意别的值后解压结果长度不符，工具报 `LayerError`。

### EV_ZLIB_HDR — zlib 封装
- 证据等级：`observed`
- 来源：载荷起点两字节为 `78 DA`（日文版全部 196 个）或 `78 01`（中文版 171 个），
  均为合法 zlib 头，`zlib.decompress` 无需 `wbits` 调整即可解出。
- 交叉验证：解出的长度与头部 `uncSize` 字段逐文件相符。

### EV_ZLIB_LEVEL9 — 压缩参数与**为什么不能重新压缩**
- 证据等级：`observed`
- 来源：日文版 196/196 个文件的原始流等于 `zlib.compress(payload, 9)` 的输出，
  即原作者用的是 zlib 默认策略 + level 9。
- **反例（关键）**：中文版 171 个 `78 01` 文件**没有任何** `(level, memLevel, strategy)`
  组合能复现原始字节流——穷举 level 1-9 × memLevel 1-9 × 5 种 strategy 全部不命中。
  说明那批文件由另一个 deflate 实现（或另一版 zlib）压缩。
- **结论**：`repack()` 在载荷 SHA-256 未变时**原样复用**原始 zlib 流，而不是重新压缩。
  这不是优化，是正确性要求：否则那 171 个文件的零编辑往返永远无法逐字节一致。
  实测该改动把 980/980 的往返一致率从 809/980 提升到 980/980。

## 3. 载荷布局

```text
偏移      字段              含义
0x00      payload_size      载荷总长 - 16
0x04      block_count       对话块数量
0x08      table_offset      偏移表起点（相对本头起点），恒等于 block_count*8
0x0C      data_offset       记录数据区起点（相对本头起点）
0x10      block_table[]     每项 8 字节：{record_count u32, first_record u32}
          offset_table[]    每项 4 字节：记录在数据区内的起始偏移
          record_stream     01 <type> <payload> 00，首尾相接无空隙
```

### EV_PAYLOAD_HDR — 载荷头四个字段
- 证据等级：`derived`
- 来源：980/980 满足 `payload_size == len(payload) - 16`。
- 交叉验证：980/980 满足 `table_offset == block_count * 8`，
  且 `(data_offset - table_offset)` 恒为 4 的整数倍。
- 未决：无。四个字段全部有可判定约束。

### EV_OFFSET_TABLE — 偏移表即引用连接的站点集合
- 证据等级：`derived`
- 来源：`(data_offset - table_offset) / 4` 项 u32，每项值等于对应记录在数据区内的偏移。
- 交叉验证一（对齐 + 范围）：980/980 满足首项为 0、全表单调递增、
  每项指向某记录的 `start` 而非内部。
- 交叉验证二（密度）：站点数恒等于记录数（245,253 条/份），比例 1:1，键域无冗余。
- 假阳性控制：`collision_class` 全部为 `unique`——每个键恰有一个站点。
- 这个集合同时充当三件事（§3）：文本发现的依据、上下文来源、变长回封的回填集合。

### EV_BLOCK_TABLE / EV_BLOCK_DERIVABLE — 块表可独立推导
- 证据等级：`derived`
- 来源：块表平铺整个记录流（游标从 0 递增，末项止于记录总数）。
- **两条独立证据**：① 块表自身的游标连续性；② 块边界可**完全独立地**
  从「每条 `0x02` 记录之后开一个新块」推导出来——980/980 份文件、38,559 个块，
  推导结果与存储值**逐项相同**。第二条是强证据：它把「块」这个概念与页结束记录绑定，
  两者互为校验。
- 反例检查：任意改动一个块的 `record_count` 都会让两种算法分歧，工具报 `StructureError`。

### EV_RECORD_SHAPE — 记录形态
- 证据等级：`derived`
- 来源：245,253 × 5 = 1,226,265 条记录全部满足 `payload[start] == 0x01`、
  末字节为 `0x00`、内部无 `0x00`。
- 交叉验证：相邻记录首尾相接（`next.start == this.end + 1`），末记录终止符恰在载荷末字节。
- 因此数据区**每字节唯一归属**，无 gap 无 overlap。

## 4. 记录类型（穷举，非采样）

按 §0.2 统计全语料的形态签名，而不是只看头几个文件。五个来源 980 个文件的
类型字节分布**完全一致**，只有四个取值：

| type | 助记 | 条数（每份） | 角色 |
|---|---|---|---|
| `0x30` | `CMD` | 139,856 | 明文命令行 |
| `0x20` | `MSG` | 41,805 | 对白 / 旁白 |
| `0x21` | `NAME` | 25,229 | 说话者名 |
| `0x02` | `PAGE` | 38,363 | 页结束，payload 恒为空 |

### EV_TYPE_CMD / EV_TYPE_MSG / EV_TYPE_NAME / EV_TYPE_PAGE
- 证据等级：`observed`
- 来源：`0x30` 记录的 payload 首词落在 305 个命令词表内（`cg`/`wait`/`pcm`/`bg`/`if`/
  `#变量赋值` 等）；`0x21` 记录的 payload 是 76 个人名之一（`航` 10,075 次、
  `雛子` 3,702 次…）；`0x02` 记录 payload 长度恒为 0（38,363/38,363）。
- 交叉验证：`0x21` 之后紧跟 `0x20` 的比例为 25,228/25,229（唯一例外见 EV_NAME_PER_BLOCK）；
  每个块的最后一条记录必为 `0x02`（38,363 个块）或 `0x30`（196 个文件的末块）。

### EV_TYPE_PAGE2 — 第二种页结束记录 `0x03`
- 证据等级：`observed`
- 来源：同引擎第二部作品 Yukikoi Melt 的 `__tar15a.cst` 有 8 条 `0x03` 记录
  （记录 3076, 3079, 3082, …），payload 恒为空。
- 交叉验证一：8/8 条全部位于其块的**最后一条**（`是块尾=True`），与 `0x02` 同位。
- 交叉验证二（决定性）：把 `{0x02, 0x03}` 一起当块终止符时，
  该作 **73/73** 个文件的块表可逐项独立推导；只用 `0x02` 则 `__tar15a.cst` 推导失败。
  这与 EV_BLOCK_DERIVABLE 是同一条判据，只是终止符集合扩大了。
- 上下文：`0x03` 出现在 `\pc` 居中排版的连续叙事段落之间，推测是「另一种翻页动画」，
  但具体差异未确认——因此只申报「它是块终止符」，不声称知道它与 `0x02` 的语义区别。
- 反例检查：イノセントガール 的 980 个文件中 `0x03` 出现 0 次，
  所以第一部作品的语料**不可能**发现它。这正是 §0.3 要求跨样本验证的理由。

### EV_PARALLEL_* — 用中文版做对照实验（最强的角色证据）
- 证据等级：`observed`
- 方法：`scene/` 目录是同一批脚本的**官方中文译本**，与 `脚本/`（日文原版）
  记录数、块表、类型字节分布**完全相同**（245,253 条逐条对应）。
  因此「哪些记录是玩家可见文本」可以直接**测量**，不必推断。

| 记录类别 | 日→中 有改动 | 总数 | 比例 | 结论 |
|---|---|---|---|---|
| `0x30` 命令 | 0 | 139,699 | 0.00% | `frozen` |
| `0x20` 有内容 | 37,355 | 38,363 | 97.37% | `translatable` |
| `0x20` 空 payload | 0 | 2,468 | 0.00% | 结构标记，见 EV_EMPTY_MSG |
| `0x20` 仅含标记 | 963 | 974 | 98.87% | `translatable` |
| `0x21` 人名 | 8,018 | 25,229 | 31.78% | `translatable`（仅假名名字需译） |
| `0x02` 页结束 | 0 | 38,363 | 0.00% | payload 恒空 |
| `fselect` 内选项行 | 30 | 30 | **100.00%** | `translatable` |
| `fselect` 本身 | 0 | 13 | 0.00% | `frozen` |
| `str NNN` 场景标题 | 0 | 114 | 0.00% | `review-required` |

- `0x21` 只改了 31.78%，因为汉字人名（`航`/`雛子`/`鼎`）中文照用，
  只有假名名字（`このか` → `小乃香`、`かがり` → `篝`）需要译。这与「人名是可翻译文本」
  一致，不构成反例。
- `str 155 雛子個別１` 一条未改：它是**存档画面显示的场景名**，中文版选择不译。
  因此标 `review-required` 而不是 `translatable`——证据不足以断言可译，如实申报。

### EV_EMPTY_MSG_BEFORE_PAGE — 零长度 MSG 是「清空文本框」
- 证据等级：`derived`
- 来源：2,468 条空 payload 的 `0x20` 记录中，**2,467 条**紧邻其块的 `0x02` 页结束记录
  （位于块内倒数第二条），唯一例外在 `OP05.cst` 记录 974。
- 交叉验证：中文版对这 2,468 条**一条未改**（EV_PARALLEL_EMPTY_UNCHANGED）——
  译者也认为这里没有可译内容。
- 处置：保留在 IR 与覆盖证书中（`exported=false`、`frozen`），**不导出到双行文本**。
  按 §4.6 的判据：译者看到一个空条目做不出任何不同的操作，写出来纯属干扰。
  实测这让双行文本从 67,178 条降到 64,710 条，少了 2,468 个空行块。

## 5. 文本规则（命令记录内的次级消歧）

两条规则，均以「已由记录类型证明是 CMD 记录」为前置，只在操作数上做切分。
逐规则命中数写进 `reports/disasm.json` 的 `rule_hits`。

### EV_FSELECT_BLOCK — 选项块
- 证据等级：`derived`
- 来源：13 处 `fselect select 1` 之后紧跟 2-4 条形如 `<数字> <跳转标签> <选项文字>` 的
  CMD 记录。
- 交叉验证一：**结构终止**——块内 30 条选项行全部连续，遇到第一条不符合该形态的记录即闭合，
  不依赖固定窗口。
- 交叉验证二：全语料中符合该形态但**不在** `fselect` 之后的记录数为 **0**，
  说明这个形态不会误命中普通命令。
- 交叉验证三：中文版把这 30 条**全部**改了（100%），且跳转标签一字未动——
  证明第三段是文本、前两段是结构。
- 回封处置：只重写第三段（`prefix` = `"0 HIN04_A "` 原样保留）。

### EV_STR_SLOT — 场景标题
- 证据等级：`derived`
- 来源：114 条 `str 155 <标题> ` 记录，槽位号恒为 155（无第二个槽位号出现）。
- 交叉验证：其后紧跟 `scene #str155`，即该槽位被场景注册命令消费。
- 交叉验证二：中文版一条未改 → 标 `review-required`，不冒充 `translatable`。

## 5.5 CSTL：多语言文本覆盖层

Yukikoi Melt 除 `.cst` 外还有 19 个 `.cstl`。不压缩、不加密、UTF-8。

```text
off   size  field
0     4     magic "CSTL"
4     4     u32 保留，19/19 文件为零
8     1     u8 语言数（3，localize.cstl 为 1）
9     var   每语言 { u8 len; ASCII 语言码 }   → 3 语言时头止于 0x12
...   var   VARINT 条目数
...   var   条目数 × 语言数 × 2 × { VARINT 字节长; UTF-8 字节 }
```

### EV_CSTL_VARINT — 长度是 0xFF 累加式变长整数
- 证据等级：`observed`
- 算法：`value = 0; while b == 0xFF: value += 255; advance; value += b`
- 来源：`__tar01.cstl` 头后为 `ff ff 17` = 255+255+23 = **533**，
  恰等于该文件的条目数（3198 个串 ÷ 6 = 533）。`ff ab` = 426，同样吻合。
- **反例检查（关键）**：按 LEB128 读 `ff ff 17` 得 380928+16256+127，无意义；
  按 u8 读则少读 1-2 字节导致整条流错位。两种错法我都实测踩过——
  「按 u8 读能读通前几条」是最有欺骗性的假信号。
- 交叉验证：19/19 文件的字节消耗量**恰好等于文件长度**，零剩余、零解码失败。
- 补充：长度落在 `0x80..0xFE` 的串用**单字节**存（不是双字节），
  全语料只有一个 258 字节的串（`__tar04.cstl` 偏移 0x108be）需要两字节长度。

### EV_CSTL_LAYOUT — 每条 = 逐语言的 (说话者, 正文)
- 证据等级：`observed`
- 来源：`__tarH04_l.cstl` 偏移 0x66d 起的一段可完整读通，给出铁证：
  `6 '垂冰'` / `48 '「我，我也想…」'` / `6 'Taruhi'` / `57 '"A-And well…"'` /
  `9 'たるひ'` / `63 '「わ、私だって…」'` —— 严格按头部语言顺序 cn/en/jp，
  每语言两个槽。旁白条目的说话者槽长度为 0。
- 交叉验证：19/19 文件的串数都能被 `2 × 语言数` 整除，且商恒等于头部声明的条目数。

### EV_CSTL_PAGE_JOIN — 条目单位是「页」，不是消息记录
- 证据等级：`derived`（可判定的等值关系，§3 意义上的引用连接）
- 来源：`.cstl` 的条目数恒等于同名 `.cst` 里 `0x02`+`0x03` 页结束记录的条数，
  **18/18** 个配对文件精确相符（533/426/569/667/498/17/246/…）。
- **为什么值得单列**：我先后拿 `0x20`（消息）条数、`0x20+0x21` 条数去比，
  两者都差一截（如 605 vs 533），一度以为结构没解对。实际是多条 `0x20`
  拼成一页。**「数量级接近但不相等」是最容易误导的信号**——它既像"快对了"
  又像"结构错了"，只有换一个计数单位才能分辨。
- 反例检查：若按消息记录对齐，`__tar01` 会差 72 条，且无法解释这个差值。

### EV_CSTL_SPEAKER_JOIN — 说话者与 .cst 逐条相同
- 证据等级：`observed`
- 来源：`.cstl` 的日文说话者槽（非空的）与 `.cst` 的 `0x21` 记录
  **4050/4050 逐条完全相同**，条数也逐文件相符（388/325/468/509/…）。
- 这是两个文件描述同一批对话的独立证据，也让 `.cstl` 的槽位角色
  （哪个是名字、哪个是正文）从推测变成观测。
- 正文侧：日文正文与 `.cst` payload 5183/5217 相同；34 处差异是内容级修订
  （18 处 `.cst` 多一个尾随 `\n`、8 处 `.cstl` 用 `0x1F` 代替 `\n`+全角空格、
  8 处真实的剧本改写）。**不是结构问题**，19/19 文件全部符合格式。
- 注意：`.cst` 的 payload 是 **cp932**，`.cstl` 是 **UTF-8**。
  两者比较前必须各按自己的编码解码，否则得到乱码。

### EV_CSTL_MAGIC
- 证据等级：`observed`
- 来源：19/19 文件前 4 字节为 ASCII `CSTL`，紧随 4 个零字节。
- 宿主线索：`YukikoiMelt.exe` 偏移 `0x50e098` 有字符串 `cstl`，
  与 `CatScene` 相邻（`0x50e088` 与 `0x50e0a0` 各一份），
  构成「场景脚本 + 多语言层」这一组扩展名常量。
- 未决：`CSTL` 魔数本身在 exe 里搜不到（可能在加壳段或运行时拼接），
  因此格式是从数据侧解出的，不是从宿主反汇编解出的。

## 6. 人名绑定

### EV_NAME_PER_BLOCK — 块内至多一条 NAME
- 证据等级：`derived`
- 来源：38,559 个块中，含 0 条 NAME 的 13,330 个、含 1 条的 25,229 个，
  **没有任何块含 2 条以上**。
- 因此绑定不需要前瞻窗口，也不需要「第一个匹配的是名字」这类顺序偏好（§4.7 明令禁止）：
  块归属本身就是绑定依据，`method = slot-ordinal`。

### EV_NAME_FOLLOWED_BY_MSG — 名字后接正文
- 证据等级：`observed`
- 来源：25,229 条 NAME 中 25,228 条的**下一条**记录就是 `0x20`。
- 唯一例外 `com01a.cst` 记录 2086：`みんな`（合唱）之后先跟三条 `pcm` 语音命令，
  隔 5 条才到正文。工具不为这一例放宽判据——它按「块内第一条实义 MSG」正常绑定。
- 歧义处理：13 个块（全部是 `ポエム` 诗歌段落）里一个名字后有 **2 条**实义 MSG。
  这些绑定标 `confidence=ambiguous` 并在 `candidates` 里保留全部候选，
  严格模式不输出确定值——不任选其一（§4.7 硬规则）。
- 实义判定：跳过只含 `\n\r`、`\@` 等标记与全角空格的 MSG。

## 7. 编码

### EV_ENCODING_CP932
- 证据等级：`observed`
- 来源：1,226,265 条记录的 payload 全部满足 `b.decode("cp932").encode("cp932") == b`，
  零条失败、零条有损。
- **反例检查（重要）**：中文版的字节流用 `gbk` 也能解码（`decode` 不报错），
  但解出的是乱码（`海からの潮風` ↔ `奀晽彊彊悂擖`）。因此**不能**用「能否解码」当判据。
  实际判据是：中文版沿用 cp932 编码表存汉字（`這樣的字` 都在 cp932 里有码位），
  所以两版共用 `source_encoding=cp932`。
- 例外：`イノセントガール/scene` 这一份有 **10 条**记录 cp932 解码失败
  （译者塞进了 `0xEA54` 之外的非法双字节）。这些条目标
  `parse_status=undecodable`、强制 `frozen`、以占位符逐字节呈现，往返仍逐字节一致。
  核心路径**不使用** `surrogateescape` / `replace`（§4.4）。
- 控制字节：日文版有 2 处 `0x0C`，中文版某份有 `0x01`/`0x09`/`0x0A`，
  全部转成 `{{0C}}` 形式的占位符，回封时按原始字节写回。

### 内联标记（不转义，按脚本文本保留）
`\@`（等待点击，2,466 次）、`\n`（换行 986）、`\r`（回车 959）、`\f`（249）、
`\pc`/`\pr`（居中/右对齐 135）、`\m`/`\w`/`\b`（少量）。
反斜杠**不是**转义前缀，原样保留；`[漢字/かんじ]` 是注音标记，也原样保留在文本里
（未拆成独立 `ruby` 条目——拆分需要证明引擎的解析规则，证据不足，如实不做）。

## 9. 回封

| 策略 | 本样本是否可用 | 依据 |
|---|---|---|
| `identity` | 可（无编辑时） | T1 前置已满足 |
| `in_place` | 可（译文不超原长时） | 每个记录槽的起止与容量已解析 |
| `pointer-rewrite` | 可 | 偏移表逐槽 join_site，引用站点集合完整 |
| `full-layout` | **不可** | 需要 T3；命令参数语义未逆向，`TIER_TOO_LOW` |

变长回封按**站点**改写：`for site in join_sites: write_u32(out, site.site_offset, new)`。
绝不按值匹配——块表的 `first_record` 字段值域与记录偏移重叠，按值改写会静默破坏块表。
实测 `preserved_value_collisions = 21`（值等于某记录偏移、但因不在站点集合中而被保留的
位置数）。这个数不为零是正常的，为零反而说明键域可能过窄。

### 对照验证（最强的回封正确性证据）
把官方中文版的 45,506 条译文当作译者输入回封日文版，产物与官方中文版对比：

```text
载荷逐字节一致  146 / 172
差异            26 个文件，共 860 条记录
  其中 859 条   中文版把该条**清空**了（本测试脚本无法表达：空译文行按 §4.6 表示未翻译）
  其中 1 条     中文版增删了控制字节，占位符集合不同，已被 PLACEHOLDER_BROKEN 正确拒绝
```

即：在能表达的全部改动上，本工具**独立重建出了官方译本的载荷**。

## 10. 未决与已知限制

- 命令参数语义未逐条逆向（`attr_def 401 402 403 404 405` 五个数、`#(1050+#300)` 变量空间
  的含义）。这是 T2 而非 T3 的原因，如实申报。
- `[漢字/かんじ]` 注音未拆成独立 `ruby` 条目，作为 msg 正文的一部分导出。
- 宿主 `InnocentGirl.exe` 里没有明文命令词表（`fselect`、`autoface` 等均搜不到），
  推测命令名在运行时经解密或哈希比对。因此命令语义证据来自**脚本侧统计**
  （305 个命令词的用法分布）与中文版对照，而非宿主反汇编。这限制了提级到 T3 的可能。
- `str` 槽位只观察到 155 一个值，不排除其他作品用别的槽位号。
- 跨样本验证覆盖**两部作品**：イノセントガール（5 个来源 980 个文件）与
  Yukikoi Melt（73 个 `.cst` + 19 个 `.cstl`）。两者形态签名分布确实不同——
  后者多了 `0x03` 记录类型，且带 `.cstl` 多语言层。这两项都是第一部作品的语料
  **不可能**发现的，验证了 §0.3「单一语料会把盲区固化成通过」这个判断。
  新增支持后回归验证旧语料：980/980 往返一致、条目数逐条不变，新分支没顶掉旧路径。
- `0x03` 与 `0x02` 的语义差异未确认（只证明了它同为块终止符）。
- `.cstl` 的 `CSTL` 魔数在宿主 exe 中搜不到，格式从数据侧解出；
  保留字段（偏移 4-7 的 4 字节）在 19 个样本中恒为零，含义未知。
