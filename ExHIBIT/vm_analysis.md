# ExHIBIT RLD 脚本格式逆向分析与证据台账

本文件是 `opcodelist.py` / `rldcore.py` / `rldir.py` / `disassembler.py` /
`assembler.py` 共同的唯一真值源。每个方言数值都在此登记来源。

- 引擎：ExHIBIT（さくらソフト系，2013 年前后）
- 样本：8 部作品 / 9 个语料 / 共 2797 个 `.rld` 文件
- 申报理解深度：**T2（anchor-resolved）**
- 已验证能力：覆盖证书、零编辑逐字节往返、文本发现与双行导出、变长回封

## 申报深度的边界

申报 T2 而非 T3：op 的**边界**完全确定（控制字给出参数个数与字符串个数，
字符串以 NUL 结尾），因此每个 op 可原样重放、文本槽位可精确定位并变长改写。
但 op 的 `code` 语义未逐条逆向 —— 只识别了带可见文本的那些。控制字高 4 位
（flags）的含义同样未知。因此**不声称**指令语义、可达性或控制流；这些字节以
结构化方式保留并原样写回。

不做这一步不影响翻译：文本站点由结构位置证明，与 opcode 语义无关。

## 1. 容器

```
偏移  宽度  含义
0x00   4    魔数 00 44 4C 52  ("\0DLR")
0x04   4    版本，全语料恒为 3
0x08   4    op 流起始偏移，全 2797 个文件恒为 0x110
0x0C   4    op 计数 —— 见 EV_OP_DELTA_ONE，此值比实际 op 数少 1
0x10   -    密文区起点
```

### EV_HEADER
- 证据等级：observed
- 2797/2797 个文件魔数与版本一致；`op_offset` 全部为 0x110。

## 2. 加密

`plain[i] = enc[i] ^ keystream[i & 0xFF]`，以 u32 为单位，自 0x10 起。

### EV_CIPHER
- 证据等级：observed
- 密钥周期 256 词。判定依据：`0x10..0x110` 区在同一作品内逐字节相同（见
  EV_ZERO_REGION），且按 `i & 0xFF` 分组后各组众数可解出全部文件。
- 交叉验证：8 部作品各自恢复密钥后，全部文件解析到精确 EOF。

### EV_CAP_NOT_MASK —— 加密词数必须只截顶
- 证据等级：observed
- 加密词数为 `j = min((size - 0x10) >> 2, 0x3FF0)`，**只截顶**，不用
  `& 0xFFFF` 掩码。
- 若改用掩码,当文件超过 256 KB 时会回绕 —— 本作唯一超过 256 KB 的脚本
  恰是 `defChara.rld`（人名表，66102 词），j 会绕回成 566，全表 97%
  保持未解密，错误边界还会落进立绘定义区。
- 实测现存若干 `defChara.rld` 在 word 556 之后可打印字符率仅 0.32，
  原盘同位置为 1.00：这类文件已被按错误 j 写回，任何 j 值都无法救回，
  只能从原盘重做。
- 回归守卫：`selftest.py` 对截顶规则设了专门断言。

## 3. 密钥静态恢复（无需注入游戏进程）

密钥完全可以从脚本文件本身推出，不需要运行游戏或注入进程。三种机制，强度递减：

### EV_ZERO_REGION —— 机制一（精确，单文件即可）
- 证据等级：observed
- 多数作品 `0x10..0x110`（256 字节 = 64 词）明文为全零，故该处密文**就是**
  keystream。GuardianPlace 481/481 个文件该区解密后为全零。
- 单个文件即可白给 64 个密钥词，无统计成分。

### EV_ZERO_REGION_NOT_UNIVERSAL —— 该假设不普遍成立
- 证据等级：observed
- 反例：`デーモンバスターズ` 在该区存 import 表（明文为
  `library,common\0...`）。硬当已知明文会注入**错误**密钥，并把同一把 key
  误拆成 3 个假分组。
- 处置：`anchor_is_valid()` 先验证全部文件该区一致，一致才用作锚点，
  否则退化为普通投票槽位。

### 机制二/三 —— 整词投票 与 逐字节道似然
- 证据等级：derived
- 剩余 192 个槽位：整词投票（按 `i & 0xFF` 取众数）或逐字节道极大似然
  （每槽 4 个字节道各 256 候选，字节模型从已解明文自举，种子取 `0x3FF0`
  截顶之后那段从未加密的尾巴）。
- **两者必须都跑，失败面互补** —— 这是实测结论，不是冗余设计：

  | 语料 | 整词投票 | 逐字节道 |
  |---|---|---|
  | hosisoraTP_01 | 5/38 | **38/38** |
  | Yotsuiro | **366/366** | 6/366 |

  任何单一估计器都会在某部作品上崩掉。由结构解析裁决取胜者。
- 投票**必须排除截顶之后的明文尾巴**，否则 >64 KB 的文件污染每个槽位。
- 所需语料规模实测：4 个文件即足够，2 个不可靠。输入不足 8 个文件时
  自动借用同目录文件辅助恢复（不导出它们）。

### EV_OP_DELTA_ONE —— 真正的验收门禁
- 证据等级：observed
- **"解析走到精确 EOF"不足以判定密钥正确。** 实测错误密钥能走到精确 EOF，
  但 op 数差得离谱（delta 有 -56、-868、-987）。
- 正确判据：`ops == op_count + 1`。加上此不变量后，8 部作品的 delta 分布
  立刻收敛为干净的 `{1: N}`。
- 分组同样只靠此门禁"剥洋葱"，绝不靠文件名。

### EV_DEF_KEY_SHARED —— def.rld 用另一套密钥，但全系列共用
- 证据等级：observed
- `def.rld` 的 keystream 与主密钥无 XOR 常量关系，是独立的一套。
- **7 部作品的 def.rld keystream 完全相同** —— 引擎内硬编码。
- 单文件无法用众数法恢复，但 `デーモンバスターズ` 的 def.rld 有 121 KB，
  池化后逐字节道法一轮解出，7 部作品全部验证通过。已存为
  `key_def_shared.json` 随工具分发。

## 4. op 编码

控制字 u32：

```
bits  0-15   code
bits 16-23   init_count   随后的 u32 参数个数
bits 24-27   str_count    随后的 NUL 结尾字符串个数
bits 28-31   flags        非保留位，含真实数据
```

### EV_OP_LAYOUT
- 证据等级：observed
- 按此布局，8 部作品 2797 个文件全部从 `op_offset` 精确走到 EOF，零残留。

### EV_OP_FLAG_NIBBLE
- 证据等级：observed
- 高 4 位**不是**保留位。实测分布：值 2 出现 32964 次、0 出现 8256 次、
  1/3/4/5/6 各数百至数千次。
- 早期分析曾把它并入 `str_count`（当作 8 位读），导致误判；修正为
  低 4 位是 str_count、高 4 位是独立 flags 字段。
- 语义未逆向。原样保留，不做校验（曾错误地断言其必须为 0，导致全库解析失败）。

### op 计数少 1
- 全 2797 个文件中，实际 op 数恒为 `op_count + 1`。末尾那条通常是
  `code=0x11` 的下一场景跳转（串形如 `exitReplay,*,0`）。
- 按 `op_count` 解析会留下 0..91 字节"尾巴"，误当 padding 就会丢结构；
  解析到 EOF 则精确落在文件末尾。

## 5. 文本站点

编码 **cp932**。实测全库 64174 个字符串**无一个**存在 cp932 解码失败字节，
因此核心路径禁用任何 `errors=` 兜底。

按 (opcode, 字符串槽位) 统计全部 64174 个字符串后确定下列站点：

| 站点 | code | 槽 | 位置 | tag | 条数 | 证据 |
|---|---|---|---|---|---|---|
| dialogue-body | 0x1C | 1 | 整串 | msg | 25626 | EV_MSG_1C |
| speaker-override | 0x1C | 0 | 整串 | name | 619 | EV_NAME_OVERRIDE |
| chara-table-name | 0x30 | 0 | 字段 3 | name | 44 | EV_CHARA_TABLE |
| scene-caption | 0xBF | 0 | 字段 6 | ui | 466 | EV_SCENE_CAPTION |
| choice-menu | 0x15 | 扫描 | TAB 字段 | choice | 33 | EV_CHOICE |
| font-family | 0x5E | 0 | 字段 30 | misc/frozen | 1667 | EV_FONT_NAME |

### EV_MSG_1C
- 证据等级：derived
- `code=0x1C` 槽 1 共 25626 条，98% 含假名/汉字，形态为完整句子。
- 反例检查：该槽在不含对话的系统脚本中不出现。

### EV_FONT_NAME —— 看起来像文本但不能翻译
- 证据等级：observed
- `code=0x5E` 字段 30 恒为 `ＭＳ Ｐゴシック`（1667 条，100% 汉字/假名）。
- 这是字体族名，改写会破坏字体选择，故导出为 `frozen`：**仍然导出**让译者
  看得见（否则无法发现漏译），但改动即拒绝。

### EV_CHOICE
- 证据等级：derived
- `code=0x15` 为选项菜单，TAB 分隔。选项标签所在字段**下标随记录变化**
  （实测 14/15/16/17 都出现过），故无法固定字段号，改用扫描：字段序号 ≥5、
  非数值、非资源路径、含假名或汉字。
- 另有不带记录外壳的裸选项串（D0152_01），单列一条规则。

### 非文本字段的判别
- 引擎脚本用**全角** `＝ ＜ ＞` 作比较运算符（如 `R1001＝4`）。
- 早期把 U+FF01–FF60 全角区并入"汉字"判定，导致纯参数记录被报成
  95–100% 日文文本。修正为只认假名与汉字区，全角符号归入非文本。

## 6. 人名显示（两级机制）

这是本作最容易出错的地方。

### EV_CHARA_TABLE
- 证据等级：observed
- `defChara.rld` 中 `code=0x30` 的串为 CSV：`id,数值,数值,姓名,,,,,,,,,,`
- 姓名在**第 4 字段（下标 3）**，共 44 条，id 3..47。
- 实测内容为真实日文姓名：勇気、桜花、愛祈、音々、蒼衣、沙夜子、影縫、巌…

### EV_NAME_OVERRIDE
- 证据等级：observed
- 对话 op（`0x1C`）的 `inits[0]` 是角色 id，`strs[0]` 是**显示名覆盖**：
  - 为 `*` 时（25007 / 25626）→ 用 defChara 表中该 id 的姓名
  - 否则（619 条）→ 直接用该串覆盖显示
- **两处都必须可翻译。** 只改表会漏 619 条屏幕上的署名；只改覆盖会漏全部
  正常对话的说话者。
- 游戏内实证（截图核对）：角色 id=7 表名为 `蒼衣`，在她自称女仆的段落显示
  为覆盖名 `メイドさん`，自我介绍之后显示表名 `蒼衣` —— 同一文件内两种并存。
  其他实测覆盖：id 11 上原 → `放送部員`、id 9 影縫 → `謎の声`、
  id 30 獣娘 → `守護者Ａ`。

### EV_NAME_SLOT_WRITEBACK —— 每句台词都给一条可编辑人名行
- 证据等级：derived
- 问题：走人名表的 21103 条说话者原先只以注释 `speaker=` 呈现,**不可编辑**。
  译者在剧本文件里看得见人名却改不动,只能去 `defChara.rld.txt` 改 44 条。
- 处置：槽 0 为 `*` 时也导出一条 `tag=name` 条目,`○` 行填**人名表解析出的
  真名**(不是 `*`),让译者编辑屏幕上实际显示的东西。
- 关键安全性质:**未改动时槽 0 保持 `*`**,人名表查表逻辑与字节完全不变。
  只有实际改动过的条目才把译名写入槽 0(此时该行变为覆盖显示)。因此
  零编辑回封仍逐字节一致 —— 实测 482/482。
- 依据是 EV_NAME_OVERRIDE 同一条:槽 0 本就是"逐行显示名"字段,同一角色
  id=7 在一个文件内同时以覆盖名和表名出现,写入真名是引擎既有行为。
- 两条路径并存,译者可任选：
  - 改 `defChara.rld.txt` 的 44 条 → 该角色全部台词一次生效,文件长度不变
  - 改剧本里的逐行 `name` 行 → 只影响该行,可让同一角色在不同场景显示不同称呼
- 条数：`name` 由 663 增至 21768。

### EV_VIRTUAL_ID1
- 证据等级：observed
- `inits[0] == 1` 共 3902 次，不在人名表中，且 `strs[0]` **恒为** `*`。
- 判定为主角内心独白／无名旁白，记为 `name_kind=virtual`：既不伪造成可编辑
  的 name 条目，也不显示错误姓名。导出时说话者标为 `-`。

### 条目排序按物理偏移
- 人名覆盖串在文件中存储于它所标注的台词**之前**（如 name 在 0x0C35、
  msg 在 0x0C40）。按规则声明顺序编号会让人名排在自己的台词之后，译者
  从上往下读顺序颠倒。
- 处置：全部条目按 `(offset, op_index, slot)` 排序后再编 idx。实测修正前
  全库 619 处乱序，修正后 0 处。

## 7. 回封

- 策略：`identity`（零编辑）/ 重排文本区（有编辑）。
- op **不含任何绝对偏移或指针**（2797 个文件验证）：控制字只有计数，字符串
  靠 NUL 定界。因此文本变长**无需重定位任何引用**，只需按序重新序列化，
  并回写头部的 `op_count`。这是本格式回封安全的根本原因。
- 变长是本地化常态，不作为错误处理。
- 变长后必须重新验证（`verify_rebuild`）：输出可被自身重新解析、覆盖仍为
  1.0、`op_count` 自洽、控制字与参数逐条未变、**已编辑内容确实出现在输出中**、
  未编辑串逐字节不变。
- 编码不可表示时报出具体字符并给候选编码，绝不静默替换为 `?`。
  注意日文原文含 `♪`(U+266A)，**gbk 无法表示**，中文目标编码应用 `gb18030`。

## 8. 未决与已知限制

- op `code` 语义未逐条逆向；只识别带可见文本的站点。故申报 T2，不申报 T3。
- 控制字 flags 高 4 位含义未知，原样保留。
- 条目增删、op 插删未实现（需 T3）。仅支持既有文本槽的变长改写。
- 跨作品验证已完成（8 部），但形态签名统计未做逐条目级别的穷举 —— 新样本
  若出现未见过的文本站点形态，会表现为该站点未被提取（而非报错）。
  缓解：报告给出每类 tag 的条数，某类为 0 时应人工复查。
