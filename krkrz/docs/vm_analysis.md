# PSB v3 剧本格式分析报告

以下结论全部来自 `../scn` 目录 264 个文件的全量测量，证据等级只有两种：
`observed`（直接字节观测）与 `derived`（确定性解析）。没有任何结论来自单个样本的推测。

## 容器结构

| 字段 | 偏移 | 类型 | 观测值 |
|---|---|---|---|
| signature | 0x00 | char[4] | 264/264 全为 `PSB\0` |
| version | 0x04 | u16 | 264/264 全为 3 |
| header_encrypt | 0x06 | u16 | 264/264 全为 0 |
| header_length | 0x08 | u32 | 264/264 全为 0x2C |
| offset_names | 0x0C | u32 | 恒为 0x2C（名称区紧跟文件头） |
| offset_strings | 0x10 | u32 | |
| offset_strings_data | 0x14 | u32 | |
| offset_chunk_offsets | 0x18 | u32 | |
| offset_chunk_lengths | 0x1C | u32 | |
| offset_chunk_data | 0x20 | u32 | 264/264 等于文件长度 |
| offset_entries | 0x24 | u32 | |
| checksum | 0x28 | u32 | `adler32(header[0x08:0x28])`，264/264 全部命中 |

校验算法由候选排除法确定：对九个偏移字段做 adler32 时全部文件命中；对
`[0x00:0x28]` 做 adler32、以及对同样区间做 CRC32 时命中数为 0。

**磁盘上的分区顺序与文件头字段顺序不一致。** 实际物理布局为
`header -> names -> entries -> strings -> strings_data -> chunk_offsets ->
chunk_lengths -> chunk_data(EOF)`。工具一律按偏移值推导顺序并校验单调性，
不假设顺序。

264 个文件的 chunk 表全部为空，因此 `unpack_mode` 判定为 `not-required`：
不存在内嵌二进制载荷，没有压缩层，也没有加密层。

## 三个会让朴素实现失败的性质

### 1. 值区是 DAG，不是树

全语料有 449,445 个子指针指向了已被另一个父节点占用的节点：相同子树只存一份，
被多处引用。按树遍历会把这些区间报告为重叠区间，从而无法通过覆盖检查。
解析器按绝对偏移做记忆化，因此字节归属仍然精确——entries 区的每个字节恰好属于
一个节点，264 个文件全部验证通过。

重序列化按 DFS 前序、首次出现优先的顺序发射节点，可以逐字节重现原始布局。

### 2. 整数宽度不可推导

存储宽度并非总是最小宽度，而且非最小的情况也无法用有符号解释：213,263 个整数
使用最小无符号宽度，19,071 个比无符号最小宽度多一个字节（例如值 `0xDA` 用
2 字节存储）。打包表的偏移宽度与计数宽度存在同样现象。

结论：宽度不能重算。每个解析出的表和标量都携带自己的
`count_width`/`element_width`，重序列化时原样重放。这是零编辑往返同一性成立的
最关键原因。

### 3. 名称 trie 含有不可达的填充槽位

名称表是由三个数组构成的 trie，从叶向根解码，某个字节由
`child_slot - charset[parent_slot]` 还原。由于同一父节点的所有子节点必须位于
`base + byte`，槽位分配会留下空隙：原始表平均每文件有 110 个不可达槽位
（全语料 29,173 个；例如某文件占用 453 个槽位，而紧凑 trie 只需 362 个）。

因此重新生成的 trie 虽然合法，却不是逐字节一致。`parse` 保留原始数组，`repack`
原样重放；只有键集合真的发生变化时才在 `semantic-rebuild` 下重新生成。

## 字符串表

偏移严格递增、取值唯一且按字节序排序、数据区紧密排布无填充——264 个文件全部
验证通过。每个字符串都至少被一个值节点引用（无孤立项）。

编码为 **UTF-8**，由排除法确定：96,391 个字符串中，48,104 个是纯 ASCII，
43,213 个能按 UTF-8 解码但**不能**按 CP932 解码，5,074 个两者皆可。不存在只能
按 CP932 解码的字符串，也不存在含 0x20 以下裸控制字节的字符串。

## 剧本语义

根对象键：`hash`、`name`、`outlines`、`scenes`。`name` 是源脚本文件名，`hash`
是 32 位十六进制值，既不等于文件的 MD5 也不等于文件名的 MD5——工具原样携带，
从不重算。

场景键：`firstLine`、`label`、`lines`、`nexts`、`spCount`、`title`，以及可选的
`texts`、`jumplabels`、`postevals`、`selectInfo`、`selects`。

`texts[]` 条目是 6 槽或 9 槽的位置数组：

| 槽位 | 作用 | 提取标签 |
|---|---|---|
| 0 | 说话人显示名（旁白为 null） | `name` |
| 1 | 次要说话人标注（通常为 null） | `name` |
| 2 | 正文，可含 `\n` | `msg` |
| 3 | 语音描述列表或 null | 非文本 |
| 4 | 整数消息 ID | 非文本 |
| 5 | 舞台状态（`data`、`env`，可选 `meswintype`） | 非文本 |
| 6 | null（仅 9 槽形态） | — |
| 7 | 回想日志行，已去除换行（仅 9 槽） | `msg` |
| 8 | 回想日志行副本（仅 9 槽） | `msg` |

观测到的元数签名（按频次降序）：`(S,N,S,L,i,D)` 15,695；`(S,N,S,N,i,D)` 8,679；
`(N,N,S,N,i,D)` 7,402；其后是各 9 槽变体。

槽位 2、7、8 保存的是同一句话，因此在 IR 中共享同一个 `group_key`——只翻译正文
而不翻译两个回想副本会导致历史记录界面与消息窗不一致。

`selects[]` 条目是含 `exp`、`render`、`selidx`、`text` 的对象；`text` 是可见的
选项标签，以 `choice` 标签提取。

## 多语言嵌套形态（`*.ks.scn`）

同一引擎的另一类剧本把正文放在**语言列表**里，而不是平铺槽位。在
`ライムライト・レモネードジャム` 的 `*.ks.scn` 上实测为 5 槽：

```text
texts[i] = [说话人, [语言项, ...], 语音列表, 消息ID, 舞台状态]
```

平铺槽位 2 是 `null`，真正的台词在 `texts[i][1][LANGUAGE_INDEX]` 这个语言项内：

| 语言项槽位 | 作用 | 提取标签 |
|---|---|---|
| 0 | 显示名（可为 null） | `name` |
| 1 | 正文，含 `%n;` 等控制码 | `msg` |
| 2 | 整数消息 ID | 非文本 |
| 3 | 回想行，已去控制码（仅 5 槽） | `msg` |
| 4 | 检索行，与槽位 3 同节点（仅 5 槽） | `msg` |

实测该作 607 个条目全为 5 槽形态，语言项 388 个为 3 槽、219 个为 5 槽。`LANGUAGE_INDEX`
固定取 0，即引擎的主语言位。

槽位 3 与 4 指向**同一个字符串节点**（偏移表复用），因此只出一条可编辑条目、另一条记为
别名；槽位 1 因为多了控制码前缀而是独立节点，必须单独翻译。

选项同样可能带语言层：`selects[].language[LANGUAGE_INDEX].text` 优先于平铺的
`selects[].text`；两者都存在时前者才是显示用的。

**漏掉这条分支的后果是静默的**：只会抽出人名，一条正文都没有，而且不报错。该作在加入
这条分支前抽出 418 条（全是 `name` 与 `ui`），加入后为 1,271 条（含 838 条 `msg`）。

## 收集原则

文本位点只沿上述已证明的结构路径收集。不做原始二进制字符串扫描，也不做“看起来像
对话”的启发式猜测。两种形态在同一次遍历里都被检查，因此同一份工具可同时处理
`*.txt.scn` 与 `*.ks.scn`，无需切换配置。

## 文本编辑的影响闭包

```
TextEntry
  -> 目标编码字节 + NUL 终止符
  -> 字符串数据区布局（偏移重算，绝不原地打补丁）
  -> 字符串偏移表元素宽度
  -> offset_strings_data / offset_chunk_offsets / offset_chunk_lengths / offset_chunk_data
  -> 文件头校验和（对偏移块做 adler32）
```

长度变化不会触及值图，因为字符串节点存的是**索引**而非偏移。只有当某次编辑需要
一个新字符串 ID、而该索引已超出节点原有宽度时才会重写节点；这种加宽会推移后续
节点，所以布局求解器会反复执行尺寸计算直到布局稳定。

字符串同一性被刻意保留：当一个字符串 ID 被多个位点引用而只有部分被翻译时，
被编辑的位点会分配新 ID，而不是静默地把它的孪生位点一起改掉。

## 未决项

- 根 `hash` 字段的算法未识别（`unresolved`）。它被逐字节保留，任何阶段都不重算。
  如果引擎会拿它校验内容，编辑后的文件可能需要重新生成该值——这需要本语料不包含
  的宿主二进制证据。
- 资源/chunk 值类型 25–28 在此未出现，其回封路径按规范实现，但未经语料验证。
- `header_encrypt != 0` 直接拒绝而非尝试解密；这些输入中不存在密钥证据。
