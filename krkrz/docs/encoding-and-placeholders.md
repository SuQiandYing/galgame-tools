# 编码与占位符

## 源编码是 UTF-8

对全语料 96,391 个字符串的排除法测量：

| 类别 | 数量 |
|---|---|
| 纯 ASCII | 48,104 |
| UTF-8 合法、CP932 非法 | 43,213 |
| 两者皆合法 | 5,074 |
| 仅 CP932 合法 | 0 |

不存在只能按 CP932 解码的字符串，因此 UTF-8 是 `observed` 结论而非假设。
264 个文件的名称表键全部是纯 ASCII（共 15,560 个键）。

IR、文件头与报告中显式记录四个编码字段，彼此绝不混用：

| 字段 | 默认值 | 含义 |
|---|---|---|
| `source_encoding` | `utf-8` | 原始字符串字节如何解码 |
| `target_encoding` | `utf-8` | 译文如何重新编码 |
| `asm_encoding` | `utf-8` | ASM 清单文件编码 |
| `dsat_encoding` | `utf-8` | DSAT 文件编码 |

长度按**目标编码后的字节数**计算，而不是字符数。无法表示的字符会被拒绝，
并给出位置与原因；绝不静默替换或丢弃。

把 `--target-encoding` 改成更窄的编码（如 `cp932` 或 `ascii`）会让原本合法的
文本导入失败。这是有意为之：有损编码是缺陷，不是警告。

## 占位符

0x20 以下的控制字节以及 0x7F 会被渲染为大写十六进制占位符，使译者无法删除或
改写它们：

```text
单字节      {{0A}}
连续字节段  {{01:02:03}}
```

严格文法为 `\{\{([0-9A-F]{2})(:[0-9A-F]{2})*\}\}`。任何看起来像占位符但不符合
该文法的写法——小写 `{{0a}}`、非十六进制 `{{XY}}`、未闭合花括号——都是硬错误，
因此被破坏的记号绝不会被当作普通文本重新编码。

本语料的字符串中**不含**裸控制字节，所以对这些文件而言占位符实际上不会出现。
但每次导入依然强制执行该机制，这正是工具面对其他作品或手工编辑过的源文件时
仍然安全的原因。

换行是另一套机制。消息中的 `\n` 是字符串数据里真实的换行字符，不是控制字节
占位符；DSAT 把它折叠成两字符序列 `\n`，使一个文本单元保持在单个物理行内，
导入时再还原。

### 导入阶段的检查项

每个单元依次检查，全部为硬失败：

1. 占位符记号序列与原文完全一致，包括顺序。
2. `ph_count`、`ph_bytes`、`ph_hash` 与 IR 记录一致。该哈希基于有序记号列表，
   因此即使数量与总字节数不变，交换两个占位符的顺序也会被检出。
3. 译文能用目标编码干净地重新编码。
4. 译文不含 NUL 字节，否则会使字符串提前终止。

占位符字节按十六进制数字原样写回，因此任意字节序列经 DSAT 往返都是逐字节精确的，
包括通过代理转义携带的非法 UTF-8 段。
